# 报告标题：用一句普通话说明主要发现与边界

本文是后续交付格式，不是一次已经发生的分析结果。所有待填项必须来自具名运行和证据。

## 一分钟结论

用两至三句话说明分析对象、最重要的观察，以及当前能否支持最终主张。
没有证据的地方写“尚未确定”，不要写“安全”或“存在漏洞”。

## 验收概览

| 问题 | 必须填写的内容 |
| --- | --- |
| 分析了什么 | 样本、硬件/固件目标、实际分析范围 |
| 实际做了什么 | 静态分析、读取历史波形、真实执行或模型推断，逐项区分 |
| 运行结果 | 成功、失败或被拒绝；失败阶段与已有材料 |
| 主要结论 | 可直接追溯的观察与尚待验证的猜测 |
| 程序检查 | 检查对象、通过/冲突/缺项，不伪造信心百分比 |
| 人工状态 | 待审、人工拒绝、已有明确批准；不能自行升级 |

## 发现了什么

每个发现给出：中文解释、具体证据位置/数值、证明范围，以及对应原始条目。
相似重复采样可以归组，但不遗漏差异，不把孤立时间点写成连续区间。

## 模型解释中哪些能保留、哪些需纠正

区分直接观察、确定性加工、推断、待验证假设与已知错误。
已知错误单独展示，并引用纠错来源。不要静默修正原模型 JSON。

## 建议验收意见

明确交付物是观察、静态结构、候选路径、重复执行差分还是其他结果。
给出“建议接受哪些部分、退回哪些主张”，不代替用户签字。

## 下一步

给出一个优先验证动作、需要的输入和判定标准，而不是泛泛写“进一步研究”。

## 身份与证据附录

必须包含 case/run、源文件位置与 SHA、逐条原始 ID 对应关系、支持检查及纠错来源。
拒绝运行没有 accepted report 时，交付失败说明，不重建没有保存的模型正文。
不同 run 不共享 support IDs；保持模型报告、确定性工具结果和人工意见的来源区别。
附录可以折叠，不让验收者为读懂结论先遍历长 ID。
